# CLAUDE.md

## Project overview

**(Token) Monitoring** — local tooling for tracking Claude Code token usage and session history. Reads the JSONL transcripts Claude Code writes to `~/.claude/projects/` and turns them into per-prompt token analytics, tool/file heatmaps, subagent attribution, cache analytics, project comparisons, and a rule-based tips engine. **No cost/pricing surface** — the model-rate table was removed 2026-07-25 (it rotted on every model launch); tokens are the unit of account here, and the cron lane's `MAX_BUDGET_USD` guard is the separate, still-live spend control.

Sibling of `analyzing/` over a local SQLite store (`better-sqlite3`) instead of DuckDB/Parquet. Inspired by [phuryn/claude-usage](https://github.com/phuryn/claude-usage); diverges in scope (expensive-prompt drill-down, skills view, tips engine, streaming-snapshot dedup) and delivery. Also an **active testbed for the `visualizing/` kit compositions** — its analytics data drives a real graphs-kit mount (§ Analytics testbed).

## Current state — local web app (sole surface)

The sole surface is an Astro **Node-adapter SSR** app (`monitoring/web/`), shaped like `designing/web` + `documenting/web` but **local-only**: token history is private, so it is **never deployed** — `output: 'server'` bound to `127.0.0.1`, whose `/api/*` routes read the live `~/.claude/monitoring.db` / JSONL.

- **Local web app** (`monitoring/web/`): Astro + `@astrojs/node` standalone; `Base.astro` (with `<slot name="head" />` for kit overlays) + layout-only `public/tokens.css`. Data layer + writers: § Architecture below. **Pages:** Overview / Prompts / Sessions (+ `/sessions/[id]` drill-down) / Projects / Skills / **Graph** (§ Analytics testbed) / **Operational** / **Proof** / **Constellation** (§ Operational-axis consumer) / **Flow** (constellation flow graph — same rails, producer `code/flow_graph`) / **Report** + **Rounds** (P3 report/round views — § Operational-axis consumer) / Tips / Settings, each with an `/api/*` JSON twin; shared `Nav.astro` + `NoCache.astro`. `security.checkOrigin` is off (localhost-only; enables the no-JS Settings + Rescan forms).

## Architecture — local web app data layer

- `web/src/data/scanner.ts` — the SOLE ingest: incremental JSONL fold into the cache (per-file mtime + byte offset in the `files` table, reads only new bytes; usage fields at `message.usage`, model id at `message.model`; dedups on `(session_id, message_id)`). Wired via `src/lib/scan.ts` → `POST /api/scan` (Settings Rescan); a first scan bootstraps a missing cache (creates + migrates it).
- `web/src/data/{db,skills,tips}.ts` — schema/migrations, skills attribution, tips engine. Pure (take a `Db`, run SELECTs); consumed by the `src/lib/*` assemblers behind the `/api/*` routes.
- `web/src/lib/{db,overview,pages,format,http}.ts` — request-time assemblers over the data layer; `db.ts` opens the cache read-only (`withDb`). The scan ingest is the lone writer (`withDbWrite`).
- Build: Astro + `@astrojs/node` standalone → `web/dist/`. `web/tsconfig.json` extends Astro's strictest preset (`@/*` → `src/*`).

## Conventions

- **Fully local — never deployed** (mechanism: § Current state). No telemetry, no remote calls for user data; never pushed to S3. Tests run offline.
- **Web-app deps are minimal.** Runtime is `better-sqlite3` (native, **Node-ABI** build via pnpm's default `allowBuilds`) under `@astrojs/node`. If `better-sqlite3` ever throws `NODE_MODULE_VERSION`, note `pnpm rebuild better-sqlite3` can be a **silent no-op** (observed 2026-07-14: ABI 141 vs 147, months-broken) — what worked was `npm run build-release` inside `node_modules/.pnpm/better-sqlite3@<ver>/node_modules/better-sqlite3`. And `import('better-sqlite3')` SUCCEEDS on a broken install (`dlopen` happens at `new Database()`), so health-check by opening a database, never by importing.
- **SQLite parameter binding always.** Any f-string / template in a SQL statement interpolates only internal, caller-controlled values (column names, placeholder lists). User-reachable values go through `?` bind params on both sides.
- **Small files with clear responsibilities.** Split a file past ~400 lines or once it accretes three distinct concerns.
- **Streaming-snapshot dedup.** The dedup key joining the `messages` table is `(session_id, message_id)`, **not** `uuid`. The ingest must honor it: `web/src/data/scanner.ts` evicts prior snapshots of the same `(session_id, message_id)` before inserting, and `web/src/data/db.ts` carries the `message_id` migration. (Claude Code re-writes each assistant message 2–3× as it streams.)

## Status emit

`monitoring/scripts/status_emit.mjs` writes `data/status/monitoring.json` (real producer, re-stamps `builtAt` every run; pin `KIT_VERSION` in lockstep with `@qagents/diagram-kit`). Registered in `scripts/build-status-all.mjs` PRODUCERS + `scripts/close.sh` `status_emit_producer()` + `scripts/write-status-placeholders.mjs` SUBS. The card stays **hidden** from `/status` (in `KNOWN_SUBS`, out of `STATUS_GROUPS`) — permanent, not pending: every mount serves `privacy:local-only` behind a 403, so no public status signal can exist.

## Log archive — `~/.claude/logs.db` (system of record)

`monitoring.db`'s lossless counterpart: Claude Code's ~30-day cleanup deletes raw transcripts, so `web/scripts/archive.mjs` folds **every** raw JSONL line verbatim into `~/.claude/logs.db` before they vanish. Spec — the two-DB split, schema, the two ingest tiers, `verify`'s settled/in-flight discriminator, `backup` = `VACUUM INTO`: `data/charters/monitoring/specs/claude-logs-db-2026-07-05/SPEC.md` (§ 2 / § 3–5 / § 7 — read § 7 before touching **archive.mjs or a red archive-scan cron**).

- **CLI:** `pnpm -C monitoring/web archive <scan|verify|stats|backup|grep|cat>` — standalone `.mjs` (better-sqlite3 falls back to the canonical checkout when a worktree lacks `node_modules`).
- **Ruling (shared-ledger-store spec § 13.3):** `monitoring.db` stays a local rebuildable cache and `logs.db` the local system of record — but if scan-vs-read `SQLITE_BUSY` pressure on `monitoring.db` grows, the store's generic concurrent-logging lane (`logs.record`, node connects with `pg` against the same DSN) is the sanctioned landing zone; adoption is monitoring's call.
- **Never deployed / never public**, same privacy rule as `monitoring.db`. Cadence: daily cron `monitoring:archive-scan:05:15` (script-direct scan+verify; LaunchAgent live).
